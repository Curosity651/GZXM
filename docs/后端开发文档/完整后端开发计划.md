# 重点项目科研管理系统完整后端开发计划

> 版本：1.0
> 基线日期：2026-09-14
> 适用团队：3名后端开发人员，前端按接口契约配合联调
> 本文是后端开发与协作的主计划；日期归档中的旧方案仅作为历史参考，发生冲突时以本文、API契约和数据库文档为准。

## 1. 项目目标与当前基线

本阶段要把现有React Mock原型建设成可部署、可联调、可追溯的Spring Boot后端系统，同时让3名开发人员能够在清晰边界内并行工作。

### 1.1 当前状态

| 范围 | 当前状态 | 后续处理 |
|---|---|---|
| React前端 | 页面和主要业务流程已经形成，数据主要来自Mock和浏览器本地存储 | 按业务模块逐步切换到真实API，不一次性删除全部Mock |
| API设计 | 已形成67个操作的OpenAPI 3.1契约和Markdown接口清单 | 三人评审后冻结为`v1`，实现必须以契约为准 |
| MySQL设计 | 已形成27张基础表的SQL设计和可读数据字典 | 评审后转换为MySQL Flyway首版迁移 |
| 参考后端 | 参考资料中存在认证、权限和项目查询基础代码 | 代码位于参考项目副本，不是当前根目录正式后端；只能评审后迁入 |

| 部署 | 尚未进入生产部署 | 先完成本地和测试环境，再规划Nginx及生产部署 |

### 1.2 已确认业务口径

| 领域 | 最终口径 |
|---|---|
| 系统层级 | 系统管理一个重点项目，重点项目下有多个课题；业务主要按课题展开 |
| 固定角色 | 系统管理员、项目技术负责人、科研助理、内部课题单位、外部课题单位 |
| 课题身份 | 牵头/承担是单位在具体课题中的成员关系，不是系统角色 |
| 单位账号 | 每家单位只有一个有效课题单位账号，一个单位可参与多个课题并承担不同课题身份 |
| 科研指标 | 科研助理向课题下发累计指标；牵头单位按时间节点分配给所有课题成员单位，合计不得低于课题要求 |
| 成果 | 成果归属课题和上传单位，不归属自筹项目；五类成果固定，专项指标属于总量子集 |
| 成果审批 | 投稿/申请前预审，取得正式材料后再次提交；科研助理初审、项目技术负责人终审 |
| 月季报 | 每课题每期最多一份，仅牵头单位创建、编辑和提交；科研助理初审、技术负责人终审 |
| 未填月季报 | 只显示实际创建或填报的报告，不替未填月份自动生成空白报告 |
| 国家材料 | 每个课题成员单位拥有独立清单；本单位编辑，牵头单位可查看所牵头课题全部单位材料 |
| 自筹材料 | 仅内部单位可访问；项目所属单位维护，内部牵头单位可查看所牵头课题全部自筹项目 |
| 归档审批 | 国家材料和配套自筹材料均不审批，上传成功后直接计入归档完成度 |
| 自定义目录 | 国家材料和自筹材料均允许有权限的所属单位增加、删除自定义文件夹；预置目录不可删除 |

## 2. 总体技术架构

采用“前后端分离、契约优先、模块化单体”，暂不拆微服务。

```text
浏览器
  │
Nginx
  ├── /             React静态资源
  └── /api/v1       Spring Boot模块化单体
                         ├── IAM：认证、用户、角色、权限
                         ├── Research：课题、成员、指标、成果
                         ├── Progress：月季报、审批、进度
                         ├── Archive：国家材料、自筹项目、归档进度
                         ├── File：对象存储抽象
                         └── Dashboard：工作台聚合
                              │
             ┌────────────────┼────────────────┐
           MySQL            Redis       Mock/MinIO/S3
```

### 2.1 技术栈

| 类型 | 选型 | 用途 |
|---|---|---|
| 语言 | Java 21 LTS | 后端开发运行时 |
| 应用框架 | Spring Boot 3.5.x | Web、配置、健康检查和应用集成 |
| 安全 | Spring Security＋JWT | 登录、接口权限和方法级授权 |
| 数据访问 | MyBatis-Plus 3.5.x | Mapper、分页、通用CRUD和查询辅助 |
| 数据库 | MySQL 8.4 | 业务数据、审批、版本和审计记录 |
| 数据库迁移 | Flyway | 管理可追溯的表结构变化 |
| 缓存 | Redis | 刷新令牌、短期权限缓存、幂等和限流 |
| API契约 | OpenAPI 3.1＋springdoc | 接口评审、Mock、客户端和文档生成 |
| 文件 | 存储适配层 | 初期Mock/本地，后续接MinIO或其他S3服务 |
| 网关 | Nginx | HTTPS、静态前端、API反向代理和上传限制 |
| 测试 | JUnit 5、Spring Security Test、Testcontainers | 领域规则、权限、API和MySQL集成测试 |

### 2.2 暂不引入

- 不拆微服务，不引入服务注册中心和分布式事务。
- 不引入消息队列、Elasticsearch、工作流引擎和Kubernetes。
- 不让MyBatis-Plus数据权限插件成为唯一授权手段。
- 不在数据库中保存文件二进制或NAS绝对路径。

```text
│   ├── config/                     # Security、MyBatis、Redis、OpenAPI
│   └── modules/
│       ├── auth/                   # 登录、令牌、当前用户
│       ├── system/                 # 用户、角色、权限、单位
│       ├── topic/                  # 项目、课题、成员关系
│       ├── indicator/              # 节点、指标、分配
│       ├── achievement/            # 成果、材料、两级审批
│       ├── report/                 # 规则、月季报、两级审批
│       ├── archive/                # 国家材料、自筹项目、目录和进度
│       ├── file/                   # 文件元数据和存储适配
│       └── dashboard/              # 工作台聚合查询
├── src/main/resources/
│   ├── application.yml
│   └── db/migration/
└── src/test/
```

每个业务模块内部统一采用：

```text
modules/<module>/
├── api/             Controller、请求DTO、响应DTO
├── application/     用例编排和事务入口
├── domain/          状态机、实体和值对象
├── repository/      本模块Mapper和数据访问
└── service/         公开服务和领域服务
```

规则：模块之间只能调用对方公开的应用服务或查询接口，不能直接调用其他模块的Mapper。

## 5. 为什么三个人能够并行

三个人并行的前提不是“完全没有依赖”，而是先把依赖变成稳定契约。

```text
A先冻结公共契约
  ├── 当前用户/权限/数据范围接口 ──→ B、C使用Stub开发
  ├── 文件上传下载接口 ───────────→ B、C使用Mock适配器开发
  └── 统一错误/分页/审计 ─────────→ 全体复用

B冻结课题成员查询契约
  ├── 报告判断牵头单位 ──────────→ C
  └── 归档判断单位课题范围 ───────→ C
```

例如B开发成果时，不需要等待A完成全部用户管理，只需要使用已经约定的`CurrentUser`和`TopicAccessService`接口；A可以先提供内存Stub，之后替换为真实实现。C同样可以根据OpenAPI实现报告和归档逻辑，不需要直接修改B的课题Mapper。

## 6. API协作机制

### 6.1 唯一接口契约

- `openapi.yaml`是前后端接口的机器级唯一契约。
- `api-reference.md`是产品和团队评审使用的可读版本。
- Controller、DTO、前端API Client和Mock Server都从同一契约产生或校验。
- 不以聊天记录、前端Mock对象或个人Controller代码作为接口标准。

### 6.2 契约冻结流程

| 步骤 | 负责人 | 产出 |
|---:|---|---|
| 1 | 调用方 | 提出业务场景、输入、输出、权限、错误和幂等要求 |
| 2 | 接口提供方 | 修改OpenAPI和可读版接口说明，不立即改业务实现 |
| 3 | A协调，三人评审 | 确认命名、公共结构、兼容性和合并顺序 |
| 4 | 提供方 | 实现服务端并完成契约测试 |
| 5 | 调用方 | 更新客户端或模块调用，完成联调 |

### 6.3 契约变更规则

| 变化 | v1处理方式 |
|---|---|
| 新增可选字段 | 可以向后兼容增加 |
| 新增接口 | 可以在`/api/v1`增加 |
| 删除字段、改变含义或类型 | 禁止直接修改；先增加替代字段并标记废弃 |
| 修改状态枚举 | 必须三人评审，前后端同时准备兼容逻辑 |
| 公共错误或认证方式变化 | 由A建立独立基础变更任务 |

## 7. 权限与数据范围协作

所有普通业务API按相同顺序校验：

1. JWT是否有效、账号是否启用。
2. 角色是否具有页面或动作权限。
3. 内外部单位属性是否满足业务要求。
4. 当前单位是否为目标课题有效成员。
5. 是否为目标课题牵头单位。
6. 目标记录是否属于当前单位。
7. 当前业务状态是否允许该动作。

### 7.1 公共权限接口

A提供稳定的公共服务，B和C只能调用，不能复制一套规则：

```java
topicAccessService.requireMember(topicId);
topicAccessService.requireLead(topicId);
topicAccessService.requireInternalUnit();
topicAccessService.requireOwnedByCurrentUnit(unitId);
```

Controller使用Spring Security声明动作权限，Service继续校验数据范围和状态。MyBatis-Plus拦截器可辅助列表过滤，但保存、提交、审批、下载等操作必须在业务服务中显式校验。

## 8. 数据库协作机制

### 8.1 表归属

| 人员 | 主要负责的数据表 |
|---|---|
| A | `sys_unit`、`sys_user`、`sys_role`、`sys_permission`、用户角色/角色权限、`file_object`、`api_idempotency`、`audit_log` |
| B | `biz_project`、`biz_topic`、课题成员关系、时间节点、指标定义、课题指标、单位指标、成果和成果材料 |
| C | 课题报告规则、报告期间、月季报、归档模板、自筹项目、归档文件夹和文件关系 |
| A审核、B/C共用 | `approval_record`、`submission_snapshot` |

### 8.2 迁移规则

- 首版27张表由A组织一次性评审，生成新的MySQL Flyway基线迁移。
- PostgreSQL旧迁移不能直接改名或继续执行。
- 任何已合并迁移不得修改，后续表结构变化只增加新迁移。
- 迁移文件使用UTC时间戳版本，例如`V202609150930__create_auth_tables.sql`。
- 每个PR最多包含本任务需要的迁移，不顺手修改其他模块表。
- 新增外键、唯一约束或状态字段时，必须同时补充正反测试和升级说明。
- A负责合并前检查迁移顺序，防止两个分支使用相同版本号。

## 9. Git与任务协作规则

### 9.1 一项任务对应一条分支

```text
feat/a/gz-001-backend-baseline
feat/b/gz-120-topic-membership
feat/b/gz-220-achievement-pre-review
feat/c/gz-310-quarterly-report
fix/c/gz-342-archive-file-scope
```

规则：

- 不直接在`main`开发，不共用功能分支。
- 一个任务只有一个负责人、一个分支和一个PR。
- 一个PR优先只完成一个业务闭环或一个公共契约变更。
- 开工前从最新`main`创建分支；合并前重新同步`main`。
- 默认Squash Merge，合并后删除远端功能分支。

### 9.2 每个任务必须写清

| 必填项 | 示例 |
|---|---|
| 业务目标 | 牵头单位为课题添加承担单位 |
| 负责人 | B |
| 允许修改路径 | `modules/topic/**`及对应测试 |
| 禁止修改路径 | `auth/**`、`report/**`、旧迁移 |
| 依赖契约 | 当前用户、单位查询、课题权限服务 |
| 验收标准 | 正常添加、重复添加拒绝、非牵头单位拒绝 |
| 测试范围 | Service、API、权限正反场景 |
| 风险和回滚 | 新迁移和接口可独立回滚的应用版本 |

### 9.3 冻结与共享区域

以下内容只能由独立基础任务修改，并由另外两人评审：

- `server/pom.xml`
- `common/`、`config/`、`auth/`
- `application.yml`
- 已合并的Flyway迁移
- OpenAPI公共响应、分页、认证和错误模型
- Nginx、Docker、CI和部署文件
- 前端路由、全局Store、全局类型和公共请求拦截器

| 角色权限管理和账号启停 | 五类成果表单和材料 | 国家材料上传、查看、下载、删除 |

| CI和集成环境基础 | 成果初审、终审、版本快照 | 月季报和归档进度统计 |

退出条件：成果、月季报和两类归档分别形成端到端业务闭环。

### 阶段4：前端逐模块联调（第5周）

联调顺序：

1. 登录、当前用户、用户和角色。
2. 课题、成员和指标。
3. 成果提交、审批和进度。
4. 月季报提交、审批和进度。
5. 国家材料、自筹材料和归档进度。
6. 工作台汇总。

每次只替换一个页面闭环的Mock；真实API稳定并通过验收后，再删除该页面对应Mock写入逻辑。

### 阶段5：全链路质量验收（第6周）

| 类别 | 必须完成 |
|---|---|
| 权限 | 五类角色的页面、按钮、直接调用API正反测试 |
| 数据隔离 | 同单位跨课题、牵头/承担、内外部单位、记录所属单位隔离 |
| 状态机 | 成果和月季报所有允许/禁止流转、退回重提和重复提交 |
| 指标 | 节点累计、课题总量、单位合计、专项子集和完成率 |
| 归档 | 每课题每单位国家材料互不覆盖；外部单位无法访问自筹；归档无审批 |
| 文件 | 上传失败、重复完成、无权下载、删除、空文件、超限和存储异常 |
| 数据库 | 空库迁移、已有版本升级、唯一约束、事务回滚、备份恢复 |
| 非功能 | 日志脱敏、健康检查、并发更新、基础性能和安全配置 |

退出条件：自动化检查通过，测试环境完成五角色业务验收，阻断级问题清零。

### 阶段6：测试部署与生产准备

- Nginx统一发布React和`/api/v1`。
- MySQL、Redis和对象存储使用独立账号及最小权限。
- 密钥全部通过环境变量或密钥管理提供，不写入仓库。
- 配置HTTPS、备份、日志轮转、监控、告警和回滚步骤。
- 先部署测试环境并完成用户验收，再安排生产上线。

## 14. PR完成定义

一个任务只有同时满足以下条件才能合并：

- 实现范围与任务说明一致，没有夹带其他模块重构。
- API变化已更新OpenAPI和可读版接口文档。
- 数据库变化使用新Flyway迁移，没有修改已合并迁移。
- 权限和数据范围在后端生效，不只隐藏前端按钮。
- 正常、异常、越权和重复请求测试通过。
- 日志不包含密码、Token、文件签名地址和真实敏感数据。
- PR写明风险、回滚方式和未完成事项。
- 指定审查人批准，CI全部通过。

## 15. 风险与处理策略

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 在参考后端上混用JPA、MyBatis-Plus和两种数据库 | 持久层重复、迁移不可执行 | 阶段0一次性统一技术栈，不边开发边切换 |
| 三人同时修改公共类型和配置 | 高频冲突、集成失败 | 共享区域由A分配唯一编辑者，独立PR处理 |
| 只按角色过滤数据 | 单位可能看到其他课题数据 | 统一调用课题关系和数据归属校验服务 |
| 前端隐藏按钮代替后端授权 | 可直接调用API越权 | Controller和Service都执行权限校验并测试403 |
| 成果/月季报退回后覆盖历史 | 无法追溯审批依据 | 每次提交递增版本并保存不可变快照 |
| 归档误接审批流程 | 业务复杂且与需求冲突 | 数据库、API和状态机均不设置归档审批 |
| 过早绑定MinIO | 存储方案变化导致业务返工 | 业务只依赖文件服务接口，存储实现可替换 |
| 大批量一次性切换前端Mock | 难以定位联调问题 | 按页面闭环逐模块替换并保留可控Mock开关 |
