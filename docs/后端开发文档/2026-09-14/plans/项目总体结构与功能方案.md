# 项目总体结构与功能方案

## 1. 方案目标

目标是建设一套可由成熟 Java 团队长期维护的重点项目科研管理系统。系统采用前后端分离架构，后端使用 Java + Spring Boot，数据库统一使用 MySQL，前端沿用 React + TypeScript。当前阶段只保存目标结构和功能方案，不创建业务数据表，也不继续扩展业务代码。

## 2. 状态标识

本文使用以下状态，避免把规划误认为完成：

- `已有原型`：前端已有 Mock 页面或业务逻辑。
- `基础代码`：后端已有初步实现，但未完成 MySQL 集成验收。
- `待开发`：只有需求或目录规划。
- `后期阶段`：本地业务稳定后再实施。

## 3. 总体架构

```text
浏览器
  │
  ├── React + TypeScript 前端
  │     ├── 页面与组件
  │     ├── 领域规则与表单校验
  │     └── API Client / JWT 会话
  │
  ▼
Spring Boot REST API
  ├── 安全层：登录、JWT、角色、操作权限、数据范围
  ├── 业务层：项目、指标、成果、报告、归档、监测
  ├── 文件抽象：本地开发存储 / 阿里云 OSS
  └── 数据访问：Spring Data JPA + 事务
  │
  ▼
MySQL
  ├── 业务主数据
  ├── 状态与版本
  ├── 审批与审计记录
  └── 文件元数据（不存放文件二进制）
```

安全原则：浏览器只负责展示和交互，登录、权限、数据范围、状态流转和关键校验必须以后端结果为准。

## 5. 后端模块内部结构

每个模块保持垂直边界：

```text
modules/<module>/
├── api/             # Controller、请求和响应 DTO
├── application/     # 用例编排、事务入口
├── domain/          # 业务实体、值对象、状态规则
├── repository/      # 仅本模块的数据访问
└── service/         # 公共业务服务或领域服务
```

模块之间通过公开 Service 或 REST 契约协作，不直接访问另一模块的 Repository 和数据实体。

## 6. 功能模块方案

### 6.1 登录、用户与权限

状态：`基础代码`。

- 用户名密码登录、退出、当前用户和 JWT 会话。
- 用户启停、密码重置、角色分配、所属单位。
- 页面权限、操作权限、项目/课题数据范围。
- 系统管理员保护和密码安全策略。
- 登录、权限拒绝和关键操作审计。

### 6.2 项目、课题与单位

状态：前端 `已有原型`，后端 `基础代码`。

- 重点项目基本信息。
- 课题新增、编辑、启停、牵头单位和负责人。
- 参研单位及牵头/参与关系。
- 用户可访问项目和课题的服务端过滤。

### 6.3 指标管理

状态：前端 `已有原型`，后端 `待开发`。

- 五类预置指标及自定义指标。
- 指标定义、版本、草稿、发布和调整。
- 项目指标向课题下发。
- 课题指标向牵头单位、承担单位分配。
- 分配数量约束、版本和调整历史。

### 6.4 成果管理

状态：前端 `已有原型`，后端 `待开发`。

- 论文、专利、软件著作权、标准、人才培养。
- 草稿、预审、正式登记、补充材料、两级审核。
- 退回、重新提交、历史版本和审核意见。
- 成果与项目、课题、单位和指标关联。
- 正式生效后才进入指标统计。

### 6.5 月报季报

状态：前端 `已有原型`，后端 `待开发`。

- 月报/季报规则、开放日、截止日和生效年度。
- 按课题和周期幂等生成任务。
- 六项模板填写、保存、提交、退回和两级审核。
- 逾期计算、补报、版本和完成进度。

### 6.6 归档管理

状态：前端 `已有原型`，后端 `待开发`。

- 项目公共材料、课题国家材料、配套自筹项目材料。
- 科技、技改、基建项目材料清单。
- 归档目录与材料要求版本。
- 上传、退回、补充、审核和完整度统计。
- 自筹项目维护和数据范围控制。

### 6.7 文件服务

状态：前端为 Mock，后端 `待开发`。

- 文件上传、下载、预览、删除和版本。
- 文件类型、大小、扩展名和内容安全校验。
- 文件与业务对象、上传人和数据范围绑定。
- 本地开发存储适配器。
- 阿里云阶段切换 OSS，业务模块不感知存储差异。

MySQL 只保存文件元数据和对象 key，不保存本机绝对路径，也不建议把大文件二进制直接写入业务表。

### 6.8 监测预警

状态：部分前端原型，后端 `待开发`。

- 指标计划值、完成值和完成率。
- 成果、报告、归档的进度聚合。
- 阈值、时间节点、逾期和偏差预警。
- 项目、课题和单位维度看板。
- 预警结果记录规则、计算时点和触发原因。

监测模块只调用其他模块的公开查询接口，不直接读取内部 Repository。

### 6.9 系统配置与审计

状态：前端有部分原型，后端 `待开发`。

- 报告周期规则、成果材料规则、归档清单配置。
- 重要配置版本和生效时间。
- 登录、审批、权限、文件和配置操作日志。
- 管理员操作记录查询。

## 7. API 分组方案

```text
/api/v1/auth/**              登录与当前用户
/api/v1/users/**             用户管理
/api/v1/roles/**             角色与权限
/api/v1/projects/**          项目、单位、课题
/api/v1/indicators/**        指标定义、发布、分配
/api/v1/achievements/**      成果及审批
/api/v1/report-tasks/**      报告任务
/api/v1/reports/**           月报季报及审批
/api/v1/archive/**           归档目录、材料及审批
/api/v1/files/**             文件上传、下载和版本
/api/v1/monitoring/**        汇总和预警
/api/v1/audit-logs/**        审计查询
```

正式开发前先形成 `docs/api/openapi.yaml`，为请求字段、响应字段、错误码、权限、分页、状态枚举和示例提供唯一契约。

## 8. MySQL 方案边界

当前只完成 YAML 配置，不创建表。后续设计遵循：

- 使用 InnoDB 和 `utf8mb4`。
- 主键策略由团队在 API 契约和表设计阶段统一确定。
- 时间字段统一以 UTC 保存，界面按业务时区展示。
- 外键、唯一约束和必要的检查在数据库与应用层共同保证。
- 审批历史、版本和审计日志采用追加思路，不能无痕覆盖。
- 表结构通过新的 MySQL Flyway 迁移管理，已合并迁移只增不改。
- 先形成数据字典和评审稿，再生成第一版 MySQL 迁移。

## 9. 非功能要求

- 安全：服务端鉴权、密码散列、最小权限、敏感数据不进日志。
- 一致性：关键写入使用事务，重复请求考虑幂等。
- 可维护性：模块边界清晰，禁止跨模块直接访问 Repository。
- 可测试性：领域规则、权限正反场景、API 集成测试。
- 可追溯性：审批、版本、文件和配置都有操作记录。
- 可部署性：配置外置、无生产密钥入库、支持健康检查和备份恢复。

## 10. 部署目标

状态：`后期阶段`。

本地功能和 MySQL 数据结构稳定后，再规划阿里云：

- Spring Boot 应用容器或云服务器。
- 阿里云 RDS MySQL。
- 阿里云 OSS 文件存储。
- HTTPS、域名、反向代理、安全组和最小网络权限。
- 自动备份、日志、监控、告警和恢复演练。

普通模块开发不得顺手修改部署结构；部署必须单独建任务并由 A 负责。
