# 课题、承担单位与科研指标两级分配需求设计

## 1. 文档目的

本设计用于重构重点项目下的课题、单位、科研指标和成果管理关系。系统仍然只管理一个固定重点项目，但科研指标不再止于课题层级，而是由课题牵头单位继续分配至实际承担单位。

本设计为后续开发文档修订和前端 Mock 原型改造的业务基线。当前阶段只确认需求，不修改前端代码。

## 2. 本次确认的核心方向

系统采用两级指标分配模式：

`科研助理 → 课题 → 课题牵头单位 → 课题承担单位 → 单位成果`

1. 科研助理创建课题、维护课题基本信息并指定唯一牵头单位。
2. 科研助理按照“指标类型＋考核节点”将重点项目指标下发至课题，不增加审批环节。
3. 课题牵头单位维护本课题的承担单位，并将课题指标分配至牵头单位自身和各承担单位。
4. 牵头单位和承担单位均为指标承担主体，均可获得成果指标。
5. 承担单位需要独立登录账号，自行填报本单位成果。
6. 同一单位只使用一个账号，该账号可以参加多个课题。
7. 单位用户上传的成果归属于“课题＋上传单位”，不处理联合成果拆分和多单位重复计数。
8. 指标采用累计口径，后一考核节点的目标不得小于前一节点。
9. 单位分配合计不得低于科研助理下发的课题考核指标，允许形成高于考核指标的单位承诺指标。
10. 系统保留现有成果预审和正式审批机制。

## 3. 对旧版规则的替代

本设计正式替代现有开发文档中的以下规则：

| 旧规则 | 新规则 |
|---|---|
| 科研指标只分配到课题 | 科研助理先分配到课题，课题牵头单位再分配到单位 |
| 课题参与单位不创建账号 | 承担单位需要单位账号并自行填报成果 |
| 每个课题建立独立课题账号 | 账号以单位为主体，一个单位账号可关联多个课题 |
| 成果由课题牵头单位统一填报 | 牵头单位和承担单位分别填报自己承担的成果 |
| 课题账号只绑定一个课题 | 单位账号可通过课题成员关系关联一个或多个课题 |

其他已经确认的月季报、归档、自筹项目、预警和成果审批规则保持不变；如果后续实施时发生直接冲突，以本设计中与课题、单位、指标和成果归属有关的规则为准。

## 4. 业务层级与核心对象

### 4.1 业务层级

```text
固定重点项目
├─ 课题
│  ├─ 课题牵头单位（唯一）
│  ├─ 课题承担单位（多个）
│  ├─ 课题考核指标
│  │  └─ 单位承诺指标
│  └─ 单位成果
└─ 项目级汇总与监控
```

配套自筹项目仍然只存在于归档材料模块，不参与本次科研指标分配。

### 4.2 核心业务对象

| 对象 | 说明 |
|---|---|
| 课题 | 重点项目下的管理单元，由科研助理创建和维护 |
| 单位 | 高校、企业、科研院所、电网公司等组织主数据 |
| 课题单位关系 | 表示某单位在某课题中是牵头单位或承担单位 |
| 指标目录 | 系统预置指标与科研助理新增的自定义指标 |
| 课题考核指标 | 科研助理下发给课题的正式考核要求 |
| 单位承诺指标 | 课题牵头单位分配给课题内各单位的执行要求 |
| 成果 | 单位账号针对某课题、指标类型和考核节点上传的业务成果 |

## 5. 角色和职责

RBAC 仍然决定账号能够访问的页面和执行的动作，课题单位关系决定账号在具体课题中的业务身份和数据范围。

| 默认业务角色 | 主要职责 |
|---|---|
| 系统管理员 | 维护账号、RBAC 角色、权限、字典和系统配置；为单位创建账号并关联课题数据范围 |
| 项目技术负责人 | 查看全部课题和单位进度，执行成果终审 |
| 科研助理 | 创建课题、指定牵头单位、维护指标目录、向课题下发考核指标、执行成果初审 |
| 课题牵头单位 | 维护本课题承担单位、分配单位指标、填报本单位成果、查看和统筹课题全部单位进度 |
| 课题承担单位 | 查看参与课题和本单位指标，填报本单位成果 |

“课题牵头单位”和“课题承担单位”作为默认 RBAC 角色提供页面与动作权限，课题单位关系进一步限制账号在具体课题中能够执行的业务。一个单位账号在不同课题中的关系分别保存；即使账号拥有牵头单位角色，也只能在被标记为牵头单位的课题中维护承担单位和分配指标。

## 6. 课题管理

### 6.1 创建与维护

科研助理在“课题指标配置”中新增课题，至少维护：

- 课题编号；
- 课题名称；
- 课题负责人；
- 研究起止时间；
- 课题简介或研究内容；
- 联系人、联系电话、邮箱；
- 唯一牵头单位；
- 备注和启用状态。

课题编号在本重点项目内唯一。课题一旦产生指标、成果、报告或归档数据，不允许直接删除，只能停用。

### 6.2 指定牵头单位

每个课题必须且只能有一个牵头单位。科研助理可以从单位库选择牵头单位；单位不存在时，可先新增单位基础信息。

指定牵头单位后，系统建立一条“课题—单位—牵头”关系。牵头单位尚无账号时，由系统管理员在用户管理中创建；已有账号时，直接增加该课题的数据范围，不重复建号。

## 7. 承担单位管理

### 7.1 添加承担单位

课题牵头单位可以在自己负责的课题中：

- 从单位库选择已有单位；
- 新增单位基础信息；
- 将单位加入或移出课题；
- 查看账号开通状态；
- 查看该单位的指标和成果完成情况。

同一个单位不能在同一课题中重复加入，也不能同时被标记为牵头单位和普通承担单位。牵头单位本身自动进入指标分配范围，无需再次添加。

### 7.2 账号创建

课题牵头单位只维护课题成员关系，不直接创建登录账号。系统管理员负责：

- 为新单位创建单位账号；
- 分配“课题承担单位”或其他适用 RBAC 角色；
- 将账号关联至一个或多个课题；
- 启停账号和重置密码。

默认按“一个单位一个账号”处理。前端 Mock 原型不扩展同一单位多人、多岗位账号等复杂场景。

## 8. 指标目录

### 8.1 预置指标

系统预置以下五类成果指标：

- 学术论文；
- 发明专利；
- 软件著作权；
- 标准规范；
- 人才培养。

预置指标继续使用现有专用成果字段、预审规则、佐证材料规则和预警逻辑。

### 8.2 自定义指标

科研助理可以新增自定义指标。至少配置：

- 指标名称；
- 指标编码；
- 计量单位；
- 指标说明；
- 是否参与节点预警；
- 是否启用。

自定义指标使用通用成果填报表单，至少包含成果名称、所属课题、上传单位、关联指标、考核节点、负责人、完成日期、说明和附件。

## 9. 第一级指标分配：科研助理下发课题指标

### 9.1 分配维度

课题考核指标的唯一业务维度为：

`课题＋指标类型＋考核节点`

同一组合只允许存在一条有效指标记录。

### 9.2 累计口径

各考核节点使用累计目标。例如中期节点论文 2 篇、验收节点论文 5 篇，表示验收时累计完成 5 篇，其中包含中期要求的 2 篇。

同一课题、同一指标类型下，后一节点目标不得小于前一节点目标。

### 9.3 下发规则

科研助理可以保存课题和指标草稿。满足以下条件后可直接下发：

- 课题基本信息完整；
- 已指定牵头单位；
- 指标类型、节点和数量合法；
- 累计节点关系合法。

下发不需要项目技术负责人审批。下发后，课题牵头单位可以开始第二级分配。

## 10. 第二级指标分配：牵头单位分配单位指标

### 10.1 分配对象与维度

可分配对象包括课题牵头单位自身和所有已加入课题的承担单位。

单位指标维度为：

`课题＋单位＋指标类型＋考核节点`

### 10.2 分配约束

对于每个“课题＋指标类型＋考核节点”：

1. 所有单位分配数量之和不得低于课题考核指标；
2. 允许单位承诺指标合计高于课题考核指标；
3. 后一节点的单位累计指标不得小于前一节点；
4. 指标未分配完整时可以保存草稿，但不能正式下发；
5. 正式下发后，各单位才能看到对应指标任务。

课题对上完成率以科研助理下发的课题考核指标为分母；单位完成率以牵头单位分配的单位承诺指标为分母。超额分配不会提高课题考核目标。

### 10.3 调整规则

课题牵头单位可以重新调整单位分配：

- 调整后单位合计仍不得低于课题考核指标；
- 某单位的新指标不得低于该单位已经终审通过的成果数量；
- 已有成果的课题、单位和指标归属不因调整自动改变；
- 每次正式下发形成一个版本，记录调整时间、操作人和调整说明。

前端 Mock 阶段只展示当前有效版本和简单历史记录，不实现复杂审批和版本回滚。

## 11. 成果填报与归属

### 11.1 成果记录原则

采用“一项成果一条全过程记录”的方式。承担单位准备一篇论文、一项专利或其他成果时，逐条发起成果记录；同一条记录贯穿投递前预审、正式投稿或申请、正式材料补充、正式成果审批和最终生效，不为不同阶段重复创建数据。

指标分配完成后，系统不按照指标数量预先生成空成果。例如某单位被分配论文 5 篇，系统只显示目标数量和缺口；该单位准备第一篇论文时自行建立第一条成果记录。

所有提交、退回、修改和审批动作均保存历史记录，包括操作人、操作时间、审批意见、提交版本和附件版本。

### 11.2 用户操作入口

单位账号登录后首先看到“我的课题”。一个账号关联多个课题时，按课题分别展示：

- 本单位承担的指标；
- 已发起成果数量；
- 预审通过数量；
- 已投稿或已申请数量；
- 已完成数量；
- 待审批成果；
- 指标缺口；
- 临近节点和预警；
- 成果发起入口。

### 11.3 成果归属规则

每项成果必须关联：

- 所属课题；
- 上传单位；
- 指标类型；
- 考核节点；
- 对应单位指标记录。

成果上传单位由当前账号自动确定，不能手工改成其他单位。账号参与多个课题时，用户先选择课题，再从该课题下本单位获得的指标中选择关联项。

本期不处理联合成果拆分、共同完成单位计数、成果在单位间转移以及一项成果冲抵多个单位指标。一项终审通过的成果只为上传单位的一个对应指标增加 1 个完成数量。

### 11.4 成果发起与投递前预审

承担单位针对本单位已下发指标逐条点击“发起成果”，填写预审所需信息。论文、专利、软件著作权和标准规范至少填写：

- 所属课题和上传单位，系统根据当前账号确定；
- 关联单位指标和考核节点；
- 成果名称；
- 负责人；
- 人员及排序；
- 单位及排序；
- 拟投稿期刊、拟申请机构或目标渠道；
- 项目标注；
- 计划投递日期；
- 预审说明和附件。

预审重点判断成果名称、人员顺序、单位排序、项目标注和投递方向是否符合要求。预审被退回时，仍然修改原成果记录并重新提交，不创建新记录。

### 11.5 正式投递与正式材料补充

预审终审通过后，成果状态变为“允许投稿/申请”。承担单位在系统外完成真实投稿、申请或送审后，回到原记录登记：

- 实际投稿、申请或送审日期；
- 期刊、受理机构或送审机构；
- 投稿编号、申请号或回执编号；
- 当前外部办理状态；
- 投递回执等阶段材料。

登记后成果进入“已投稿/已申请”阶段，该阶段用于展示过程进度，但不计入指标完成数量。取得录用通知、受理证明、授权证书、登记证书或送审稿等正式材料后，承担单位继续在原记录中补充正式信息和附件，并提交正式成果审批。

### 11.6 完整审批流程

论文、专利、软件著作权和标准规范采用以下完整流程：

```text
成果草稿
  → 预审初审中
  → 预审终审中
  → 允许投稿/申请
  → 已投稿/已申请
  → 正式成果草稿
  → 正式初审中
  → 正式终审中
  → 已生效
```

退回规则如下：

- 科研助理可以在预审初审和正式初审时退回；
- 项目技术负责人可以在预审终审和正式终审时退回；
- 退回后由原上传单位修改原记录并重新提交；
- 每次重新提交增加记录版本，历史审批意见继续保留；
- 已生效成果不得直接修改关键归属和认定字段。

人才培养以及明确不需要投递前预审的自定义指标，从“正式成果草稿”开始。自定义指标是否需要预审由指标目录配置决定。

### 11.7 审批职责与计数

预置成果继续执行现有流程：

- 科研助理初审；
- 项目技术负责人终审；
- 只有终审通过并生效的成果计入指标完成数量。

课题牵头单位可以查看本课题所有单位成果、退回状态和完成情况，负责协调与催办，但本期不额外增加一层正式审批，避免改变已经确认的两级审批机制。

### 11.8 进度阶段口径

| 阶段 | 统计含义 | 是否计入完成指标 |
|---|---|---|
| 未发起 | 已分配但尚未建立成果记录的指标缺口 | 否 |
| 已发起 | 已建立成果记录，包含草稿和预审中的记录 | 否 |
| 预审通过 | 已允许投稿、申请或送审 | 否 |
| 已投递 | 已登记真实投稿、申请或送审信息 | 否 |
| 正式审核中 | 已取得正式材料并提交认定 | 否 |
| 已生效 | 正式终审通过 | 是 |

### 11.10 论文成果表单

论文表单分为基本信息、论文作者和附件三个区域。

#### 基本信息

| 字段 | 处理方式 |
|---|---|
| 论文名称 | 必填；投递前预审的核心字段 |
| 论文状态 | 投稿、录用、发表；根据流程阶段更新 |
| 投稿日期 | 完成真实投稿后填写 |
| 录用日期 | 取得录用通知后填写 |
| 发表日期 | 正式发表后填写，补充现有成果字段 |
| 专业领域 | 必填，下拉选择 |
| 战略方向 | 必填，下拉选择 |
| 关联项目名称 | 自动带出当前固定重点项目 |
| 所属课题 | 根据成果树和当前单位可访问课题选择 |
| 关联单位指标 | 从本单位已下发的论文指标中选择 |
| 论文类型 | 期刊论文、会议论文 |
| 检索情况 | SCI、EI、其他、无；允许多选适用项 |
| 期刊名或会议名称 | 预审阶段填写拟投目标，正式阶段更新实际信息 |
| 期刊级别 | 下拉选择；会议论文不适用时隐藏 |
| 发表卷期 | 正式发表后填写 |
| 所在页数 | 正式发表后填写 |
| 所属公司、所属部门 | 根据当前单位账号自动带出；无部门信息时可为空 |
| 项目标注 | 预审必填，默认带出重点项目名称和编号 |
| 备注 | 选填，限制合理长度 |

#### 论文作者

作者使用可排序明细表，支持选择、新增、删除和调整顺序。每行至少包含作者姓名、作者单位；系统根据第一行自动识别第一作者。需要保留全部作者顺序，并允许标记通讯作者。

#### 论文附件

参考图片中的材料类别为：

- 论文材料，包括封面、目录页和论文正文；
- 录用通知书；
- 检索证明；
- 其他材料。

附件要求按流程阶段判断：预审阶段至少上传论文草稿或投稿材料；正式认定时，根据论文状态要求录用通知、正式论文或检索证明。一个材料类别允许上传多个文件并保留版本。

### 11.11 专利成果表单

专利表单分为提案基本信息、发明人、申请人和提案申请附件四个区域。参考图片采用“提案申请”概念，本系统将其作为专利投递前预审记录，预审通过后继续在同一记录上补充正式申请和授权信息。

#### 提案基本信息

| 字段 | 处理方式 |

| 提案编号 | 保存后由系统生成或按业务编号规则维护 |
| 申请部门 | 根据当前单位账号带出，可由有权限人员调整 |
| 专利类型 | 发明、实用新型、外观设计 |

| 同时生成提案编号 | 条件字段 |
| 是否高价值专利培育项目 | 是或否 |
| 是否按高价值专利培育流程 | 是或否 |
| 技术领域 | 必填，可选择业务技术分类 |

| 战略方向 | 必填，下拉选择 |

| 是否发表论文 | 是或否 |
| 是否来自第三方 | 是或否 |
| 是否提前公开 | 是或否 |
| 是否申请快速预审 | 是或否；决定是否要求快速预审材料 |

| 项目标注 | 默认带出重点项目信息 |

#### 发明人

发明人使用有序明细表，至少包含发明人姓名和所在单位，支持上移、下移和删除。系统从第一行自动识别第一发明人，并补充维护：

- 第一发明人身份证号；
- 技术联系人；
- 技术联系人电话；
- 技术联系人邮箱；
- 委托代理机构。

#### 申请人

申请人使用有序明细表，保存申请人名称及排序。存在多个申请人时填写共同申请理由。申请人顺序属于投递前预审核心内容，预审通过后变更必须重新提交预审。

#### 提案申请附件

参考图片中的材料类别为：

- 技术交底书，必传；
- 专利合作申请协议，多申请人时要求上传；
- 快速预审承诺书，申请快速预审时要求上传；
- 专利布局报告，高价值培育等适用场景上传；
- 创新梳理表；
- 其他材料。

预审通过并正式申请后，在原记录补充申请号、申请日、受理回执号、受理日；获得授权后补充授权日、专利号、授权公告号、专利权人和法律状态，并上传受理或授权证明材料。

## 12. 页面与交互设计

### 12.1 科研助理端

“课题与指标配置”拆分为两个主要页签：

1. **课题管理**：新增、编辑、停用课题，维护基本信息和牵头单位；
2. **课题指标下发**：选择课题和考核节点，配置预置或自定义指标，保存草稿并下发。

新增“指标目录”入口，用于维护自定义指标。

### 12.2 课题牵头单位端

新增：

1. **承担单位管理**：维护课题成员单位和账号状态；
2. **单位指标分配**：以“指标类型＋节点”为行、课题单位为列录入分配数量；
3. **课题成果汇总**：查看所有单位的目标、完成、缺口和成果明细。

牵头单位自己的指标与其他承担单位使用同一套分配和统计规则。

### 12.3 承担单位端

新增或调整：

1. **我的课题**：展示账号关联的全部课题；
2. **我的指标**：按课题、指标类型和节点查看本单位任务；
3. **成果填报**：只允许针对本单位已下发指标逐条发起成果，并在原记录上完成预审、投递登记和正式材料补充；
4. **成果查询**：查看本单位成果和审批状态。

### 12.4 成果管理树

成果管理使用左侧树形导航和右侧列表详情布局：

```text
固定重点项目
├─ 课题一
│  ├─ 学术论文
│  ├─ 发明专利
│  ├─ 软件著作权
│  ├─ 标准规范
│  ├─ 人才培养
│  └─ 自定义指标
├─ 课题二
│  └─ 各成果类型
└─ 其他课题
```

点击成果类型后，右侧按一条成果一行展示成果名称、上传单位、负责人、考核节点、投递状态、审批状态、更新时间和操作入口。

不同身份看到的树和数据范围为：

- 科研助理、项目技术负责人：全部课题和全部单位成果；
- 课题牵头单位：自己牵头课题下的全部单位成果，以及作为普通承担单位参加其他课题时的本单位成果；
- 课题承担单位：本单位参加的全部课题，但每个课题中只显示本单位成果。

列表提供“全部、待预审、已退回、允许投递、已投递、正式审核中、已生效”等快捷筛选。科研助理可在同一页面查看详情、审批和观察阶段进度。

### 12.5 管理监控端

指标监控形成三级查看：

`项目总览 → 课题汇总 → 单位明细`

项目技术负责人和科研助理可查看全部课题；课题牵头单位可查看本课题全部单位；承担单位只查看本单位。

## 13. 状态与数据流

### 13.1 课题指标状态

`草稿 → 已下发 → 已调整`

草稿对牵头单位不可执行分配。已下发和已调整均表示当前有效版本可供分配。

### 13.2 单位指标状态

`分配草稿 → 已下发 → 已调整`

只有已下发或已调整的当前版本对承担单位可见。

### 13.3 课题单位关系状态

`待开通账号 → 正常 → 已停用`

移出单位前，应检查未完成指标、成果和业务数据。存在关联数据时不物理删除关系，只允许停用。

### 13.4 成果状态

成果状态需要明确区分预审、外部投递和正式认定：

- 预审草稿；
- 预审初审中；
- 预审终审中；
- 预审退回；
- 允许投稿/申请；
- 已投稿/已申请；
- 正式成果草稿；
- 正式初审中；
- 正式终审中；
- 正式退回；
- 已生效。

“允许投稿/申请”和“已投稿/已申请”是两个不同阶段：前者表示内部审批许可，后者表示承担单位已经登记真实外部投递行为。

## 14. 建议数据结构

| 实体 | 关键字段 |
|---|---|
| Topic | id、code、name、principalName、startDate、endDate、leadingUnitId、contact、status |
| ProjectUnit | id、name、shortName、unitCategory、统一标识、联系人 |
| TopicUnitMembership | id、topicId、unitId、membershipType、status、joinedAt |
| IndicatorDefinition | id、code、name、unit、builtIn、warningEnabled、enabled |
| TopicIndicator | id、topicId、indicatorDefinitionId、nodeId、targetQuantity、status、version |
| UnitIndicatorAllocation | id、topicIndicatorId、topicId、unitId、allocatedQuantity、status、version |
| Achievement | 增加 topicUnitMembershipId、uploadUnitId、unitIndicatorAllocationId、externalSubmissionStatus、actualSubmissionDate、submissionReference、version |
| AchievementParticipant | achievementId、participantType、name、unitName、sortOrder、identityFields；用于作者、发明人、申请人和著作权人明细 |
| AchievementAttachment | achievementId、materialType、fileName、fileUrl、version、uploadedBy、uploadedAt |
| ApprovalRecord | 关联成果、预审或正式阶段、初审或终审层级、决定、意见、操作人、操作时间和成果版本 |
| User | 保留 roleId、dataScope；增加 unitId；单位账号的可访问课题由有效课题单位关系计算 |

实现时不再将 `participatingUnitIds` 作为课题参与关系的唯一数据来源，应使用独立的课题单位关系实体，以支持状态、账号和多课题复用。

单位业务账号不再手工维护重复的 `topicIds` 作为课题权限来源。系统管理员只负责账号与单位绑定，具体可访问课题由该单位当前有效的课题单位关系自动得到；项目技术负责人、科研助理等管理账号仍可使用全项目数据范围。

## 15. 统计口径

### 15.1 单位完成率

`单位终审通过成果数 ÷ 单位承诺指标数`

按课题、指标类型和考核节点分别计算，展示完成数量、缺口和完成率。

### 15.2 课题考核完成率

`课题内全部单位终审通过成果数 ÷ 课题考核指标数`

完成数量可以超过课题考核指标；页面完成率显示可封顶为 100%，同时单独展示超额完成数量。

### 15.3 课题内部履约率

为便于牵头单位管理，可以另外展示：

`课题内全部单位终审通过成果数 ÷ 单位承诺指标合计`

该指标只用于内部履约管理，不替代课题对上考核完成率。

### 15.4 成果过程进度

每个课题、单位和成果类型同时展示：

- 分配数量；
- 已发起数量；
- 预审通过数量；
- 已投稿或已申请数量；
- 正式审核中数量；
- 已生效数量；
- 剩余缺口；
- 各阶段停留时长和临期预警。

“剩余缺口”始终以已生效数量计算，不能用已发起、预审通过或已投递数量代替。

## 16. 异常处理与约束

- 未指定牵头单位的课题不能下发指标；
- 未下发课题指标时不能进行单位分配；
- 单位分配合计不足时不能下发；
- 单位未加入课题时不能获得指标或上传该课题成果；
- 单位只能针对本单位已下发指标发起成果；
- 未通过投递前预审的成果不能登记为已投稿或已申请；
- 没有正式认定材料的成果不能提交正式成果审批；
- 退回成果必须在原记录上修改和重新提交，不能通过新建记录规避审批历史；
- 账号未开通时单位关系可以保留，但不能登录办理；
- 角色停用、账号停用或课题单位关系停用后，不允许新增和提交业务数据；
- 已产生业务数据的课题、单位关系、指标和账号禁止物理删除；
- 自定义指标停用后保留历史数据，不允许新增成果。

## 18. 验收场景

1. 科研助理可以新增课题、完整填写基础信息并指定牵头单位。
2. 科研助理可以配置预置和自定义指标，并按累计节点直接下发至课题。
3. 课题牵头单位可以添加多个承担单位，牵头单位自身自动参与指标分配。
4. 系统管理员可以为单位创建账号；已有单位账号可增加多个课题范围。
5. 课题牵头单位可以将课题指标分配到各单位，合计不足时不能下发。
6. 单位账号登录后只能看到其参与课题和本单位指标。
7. 同一账号参与多个课题时，可以在课题之间切换并分别完成对应指标。
8. 单位用户可以逐条发起成果，同一记录依次完成预审、外部投递登记、正式材料补充和正式审批。
9. 未通过预审的成果不能登记为已投稿或已申请，只有正式终审通过后对应单位指标完成数量才增加 1。
10. 成果管理按“课题—成果类型”树形展示，科研助理可以查看全部成果、办理初审并查看阶段进度。
11. 论文表单能够维护作者顺序、检索信息以及论文、录用和检索材料。
12. 专利表单能够维护提案信息、发明人、申请人顺序以及按条件要求的申请附件。
13. 软件著作权表单能够维护著作权人、技术环境、主要功能和鉴别材料。
14. 牵头单位可以查看本课题各单位目标、完成数量、缺口和成果状态。
15. 科研助理和项目技术负责人可以从项目总览下钻到课题和单位明细。
16. 调整单位指标后，课题分配合计仍不得低于课题考核指标，也不得低于单位已完成数量。
17. 月季报、归档、自筹项目和规则预警功能继续保留，不因本次改造被删除。

## 19. 明确不纳入本期的内容

- 联合成果按比例拆分；
- 一项成果同时冲抵多个单位指标；
- 将预审申请与正式成果拆分为两条独立业务记录；
- 按指标数量预先生成空成果记录；
- 单位之间转让已有成果；
- 指标分配审批流程；
- 同一单位多用户、多部门和岗位体系；
- 承担单位直接维护月季报、国家归档或配套自筹项目材料；
- 配套自筹项目承接科研成果指标。

上述内容如未来确有业务需要，应作为独立需求评审，不在本次原型中预留复杂流程。
